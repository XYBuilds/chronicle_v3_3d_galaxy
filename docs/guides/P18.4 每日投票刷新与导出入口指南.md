## 1. P18.4 在整条链路里做什么

| 环节 | 说明 |
|------|------|
| **输入** | Kaggle 数据集 `alanvourch/tmdb-movies-daily-updates`（与 `data/raw/TMDB_all_movies.csv` 同型宽表），或本地 `--input-csv` 指向的 raw 快照。 |
| **冻结门槛** | 从 Supabase 表 **`threshold_versions`** 中读取 **`is_active = true`** 的那一行的 **`thresholds_json`**（按上映年 → 最低 `vote_count`）。**每日任务不得重算**动态门槛，避免老片在门槛边缘反复进出宇宙。 |
| **清洗** | `scripts/pipeline/cleaning.py`：`run_cleaning_pipeline(..., frozen_year_thresholds=...)`，在 dedup + 必丢规则之后用**冻结**逐年门槛过滤，得到当日「应出现在宇宙中」的候选集合。 |
| **对库 diff** | 与 **`movies`** 对比：已有 `id` → 若 `vote_count` / `vote_average` / `popularity` 变化则 **upsert** 整行（保留 `x,y,z` 等坐标）；**新过线且不在 `movies`** 且不在 **`movies_pending`** → 算 **MiniLM 文本向量 + genre/lang 向量**，**INSERT `movies_pending`**（供 P18.5 月度 refit 合并）。 |
| **不做的** | **不**更新 `threshold_versions`；**不**因当日低于冻结门槛而从 `movies` **删除**老片（仅统计「低于门槛仍在库中」的数量）；坐标变更留给 **P18.5**。 |
| **月初快照** | 当 UTC 日期为 **每月 1 日** 时，向 **`vote_snapshots`** 批量 **upsert** 当前全库 `vote_count` / `vote_average`（主键 `movie_id` + `snapshot_month`）。 |
| **导出** | `scripts/cron/export_from_supabase.py`：分页读取 **`movies`**，拼出与 `export_galaxy_json` 一致的 payload，写入 `frontend/public/data/galaxy_data.json`（及 `.gz`、搜索索引）。`meta.version` 形如 `YYYY.MM.DD.daily.<seq>`。 |
| **CI** | `.github/workflows/nightly_vote_refresh.yml`：定时 + `workflow_dispatch`，上传导出物为 **artifact**；配置 **`CLOUDFLARE_*`** Secrets 后对 **Cloudflare Pages** 执行 Direct Upload（见 [P18.6 Cloudflare Pages 切换操作指南](./P18.6%20Cloudflare%20Pages%20切换操作指南.md)）。 |

## 2. 你需要先满足的前提

1. **Supabase 已按 P18.2 建表**，且 **`movies`** 中已有与当前宇宙一致的数据（通常由 `scripts/supabase/initial_import.py` 导入，约 59k 行）。  
2. **在下载 Kaggle 前通过只读 preflight**：运行 `python scripts/cron/check_supabase_health.py`，确认输出 `category=ok`、`active_threshold_count=1` 与合理的 `years_min/years_max`。失败时按 `config_missing`、`url_invalid`、`dns_failure`、`tls_failure`、`auth_failure` 或 `active_threshold_cardinality_failure` 修复；日志不得包含 URL 或 key 原文。
3. **本机或 CI 已安装依赖**：`pip install -r requirements.cpu.txt`（内含 `supabase`、`python-dotenv`、**`kaggle`** 等）。
4. **根目录 `.env`**（仅本地，勿提交）或 CI **Secrets** 中配置：
   - `SUPABASE_URL`
   - `SUPABASE_SERVICE_ROLE_KEY`（与 P18.2 导入脚本相同，**不要用 anon key**）

## 3. 必做的一次性步骤：写入「当前生效」的冻结门槛

**原因**：`scripts/cron/nightly_vote_refresh.py` 启动后会查询 **`threshold_versions`** 中 **`is_active = true`** 的行。若不存在，脚本会直接报错退出，后续 diff/写库都不会执行。

**脚本**：`scripts/cron/seed_active_threshold_version.py`

**行为简述**：

1. 读取 **raw** CSV（默认 `data/raw/TMDB_all_movies.csv`，可用 `--input` 指定）。  
2. 执行与管线一致的 **门槛前** 清洗：`run_cleaning_pipeline_before_vote_threshold`。  
3. 在该结果上调用 **`compute_year_to_vote_threshold`**，得到与 `apply_dynamic_vote_threshold` 相同规则的逐年字典。  
4. 将库内所有 `threshold_versions` 的 **`is_active`** 先置为 `false`，再 **INSERT** 新版本行并设 **`is_active = true`**，写入 `quantile` / `alpha` / `rolling_window` / `abs_min` / **`thresholds_json`** 等字段。

**本地执行示例**（PowerShell，仓库根目录）：

```powershell
# 建议先 dry-run（不写库，仅验证能读到 raw 并算出门槛规模）
python scripts/cron/seed_active_threshold_version.py --input data/raw/TMDB_all_movies.csv --dry-run

# 确认无误后写入 Supabase（需 .env 或环境变量中有 URL + service_role）
python scripts/cron/seed_active_threshold_version.py --input data/raw/TMDB_all_movies.csv --version-label p18_bootstrap_v1
```

**注意**：

- **`--version-label`** 对应表主键 **`version`**；若重复执行且未改标签，会因主键冲突失败。  
- 重新播种时通常应使用**新版本号**，并理解脚本会**取消**旧行的 `is_active`。  
- raw 文件体积很大，请在**本机终端**运行，勿在对话中打开整文件。

## 4. Kaggle 凭证（仅 nightly 从 Kaggle 拉数时需要）

Workflow 与默认的 `nightly_vote_refresh.py`（不传 `--input-csv`）会调用 **`python -m kaggle datasets download ...`**。

任选一种方式即可：

| 方式 | 说明 |
|------|------|
| **GitHub Secrets** | 配置 `KAGGLE_USERNAME`、`KAGGLE_KEY`（与 Kaggle Account → API 页面一致）。workflow 已引用。 |
| **本机 `~/.kaggle/kaggle.json`** | 按 Kaggle 官方说明放置 JSON；或在本机 shell 中设置同上两个环境变量。 |

**本地不下载 Kaggle、仅用子样 CSV 冒烟**（先完成只读 preflight；nightly 会只读当前 frozen threshold 并跑完整清洗逻辑，**不写库**）：

```powershell
python scripts/cron/check_supabase_health.py
python scripts/cron/nightly_vote_refresh.py --input-csv data/subsample/TMDB_all_movies_random20.csv --dry-run
```

dry-run 日志应包含 active threshold version、冻结门槛的年份数量、`cleaned.shape` 与 `--dry-run: skip Supabase writes / export`。它不执行任何 upsert、pending insert 或导出部署。

若要**写库 + 导出**（慎用，需真实 Supabase 与已 seed 的 `threshold_versions`）：

```powershell
python scripts/cron/nightly_vote_refresh.py --input-csv data/subsample/TMDB_all_movies_random20.csv
# 子样行数少，对全库 59k 的 vote 更新意义不大，一般仅作连通性测试
```

## 5. 仅重新导出静态 JSON（不写 Kaggle、不跑 nightly）

适用于：Supabase 里 `movies` 已由别的方式更新完毕，只想刷新 `frontend/public/data/` 下产物。

```powershell
python scripts/cron/export_from_supabase.py
# 可选：只写 gzip，减小体积
# python scripts/cron/export_from_supabase.py --skip-plain-json
```

然后可用：

```powershell
python scripts/validate_galaxy_json.py --input frontend/public/data/galaxy_data.json
```

**CI 中的版本后缀**：workflow 会设置 `GALAXY_EXPORT_SEQ`（默认取 `github.run_number`）；本地可手动：

```powershell
$env:GALAXY_EXPORT_SEQ = "manual1"
python scripts/cron/export_from_supabase.py
```

## 6. GitHub Actions：启用 nightly 后要做什么

**文件**：`.github/workflows/nightly_vote_refresh.yml`

| 配置项 | 说明 |
|--------|------|
| **触发** | Cron：`0 20 * * *`（UTC 每日 20:00）；以及 **`workflow_dispatch`** 便于你手动点一次验收。 |
| **Secrets** | `SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY`、`KAGGLE_USERNAME`、`KAGGLE_KEY`。 |
| **资源** | `ubuntu-24.04`，`timeout-minutes: 60`；与 benchmark workflow 类似设置了 `OMP_NUM_THREADS` 等，减轻 BLAS 过度订阅。 |
| **产物** | Artifact：`galaxy_data.json`、`.gz`、`galaxy_search_index.json.gz`。 |
| **部署** | 当前**未**接 Cloudflare Pages；合并 P18.6 时取消注释并配置 `CLOUDFLARE_*` 等 Secrets 即可。 |

**推荐验收顺序**：

1. 在 Supabase 中确认 **`threshold_versions`** 已有 `is_active = true` 行（第三节）。  
2. 在 GitHub 配好上述 Secrets。  
3. 打开 **Actions → P18.4 Nightly vote refresh → Run workflow** 手动跑一次。  
4. 检查 Job 日志中的统计行：`vote_updates`、`below_threshold_observed`、`new_pending_candidates`。  
5. 下载 **artifact**，必要时对比与上一版 `galaxy_data.json.gz` 的体积与 `meta.version`。

## 7. 常见问题与排错

| 现象 | 可能原因 | 处理方向 |
|------|-----------|----------|
| `no active threshold_versions row` | 未跑 seed 或全被置为 inactive | 第三节重新播种并确认 `is_active`。 |
| Kaggle `401` / `403` | Secrets 错误或 API key 撤销 | 检查 Kaggle 账号 API；本机检查 `kaggle.json`。 |
| `supabase` 连接失败 | URL/key 错误、网络、项目暂停 | Dashboard 确认项目状态；勿混用 anon。 |
| `movies` upsert 报错缺列 | 行字典字段与表结构不一致 | 对照 `supabase/migrations/20260504120000_p18_2_schema.sql`；升级脚本后同步 cron 映射。 |
| `movies_pending` insert 失败 | `overview` 为空、genre 不在冻结表、BYTEA 维度不对 | 看日志中具体 id；确认 P18.0 genre 冻结与 MiniLM 384 维。 |
| `validate_galaxy_json` 失败 | 导出字段与 Tech Spec §4.3 不一致 | 先修 `export_from_supabase` 与 `build_galaxy_payload` 的列映射，再重跑。 |

## 10. 小结：按顺序执行的「待办清单」

1. **Supabase**：P18.2 DDL 已应用，`movies`（及可选 `galaxy_v1_reference`）数据就绪。  
2. **一次性**：`seed_active_threshold_version.py` 写入 **`threshold_versions`** 且 **`is_active = true`**。  
3. **Secrets**：GitHub 配置 `SUPABASE_*` 与 `KAGGLE_*`；本地 `.env` 与/或 Kaggle 凭证。  
4. **验证**：`workflow_dispatch` 跑通 nightly；检查日志与 artifact；`validate_galaxy_json` 通过。  
5. **之后**：推进 P18.5（月度 refit）、P18.6（CF Pages 部署接线）、P18.7（文档与验收）。

按上述顺序做完，P18.4 的「每日轻刷新 + 静态导出」路径即处于可运营状态；剩余工作主要是月度算力与前端托管策略，而不是再改 nightly 的核心契约。

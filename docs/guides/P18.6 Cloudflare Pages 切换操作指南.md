# P18.6 Cloudflare Pages 切换操作指南

本指南说明 **Phase 18.6** 落地后，你在 **Cloudflare 控制台、DNS、GitHub Secrets** 侧需要完成的配置与验收顺序。

**职责划分（P18.6 + P18.6b）**

- **Pages**：托管前端静态产物（`pages-action` 上传 **`frontend/dist`**）。Cron 在写出 `frontend/public/data/*` 后会 **安装依赖并 `npm run build -w frontend`**，再部署。
- **R2（P18.6b）**：托管 **`galaxy_data.json.gz`** 等**超过 Cloudflare Pages 单文件 25 MiB 上限**的大对象；浏览器从 **R2 公开 URL**（或自定义域）拉取 gzip，**不依赖**把该文件打进 Pages 部署包。

总体规划见 `.cursor/plans/phase_18_data_infrastructure_9ccb7a3f.plan.md` 中 **P18.6 / P18.6b** 小节。R2 上传与前端 URL 的**代码接线**以仓库后续 PR 为准；本指南先固定**控制台与密钥**侧约定。

**建议先读完**：

- [P18.4 每日投票刷新与导出入口指南](./P18.4%20每日投票刷新与导出入口指南.md)（nightly、导出、`GALAXY_EXPORT_SEQ`）
- [P18.5 月度星系 refit 操作指南](./P18.5%20月度星系%20refit%20操作指南.md)（月度、四件套、`monthly_refit_meta.json` artifact）

**与 P18.5b 的关系**：部署步骤在 Python job **全部成功**之后执行；锚点 **软闸** 不会单独阻止上传 Pages（硬闸/脚本失败导致 job 失败时自然不会部署）。

## 1. 你要完成的待办清单（推荐顺序）

1. 在 Cloudflare 创建 **Pages** 项目（类型须为 **Pages**，不是仅带 `wrangler deploy` 的 Worker Git 项目），并记下 **Account ID**、**项目名称**（与下面 `CLOUDFLARE_*` Secret 一致）。
2. 创建 **API Token**（权限见第 3 节），写入 GitHub Secret **`CLOUDFLARE_API_TOKEN`**。
3. 在 GitHub 仓库 **Settings → Secrets and variables → Actions** 中补齐三个 **`CLOUDFLARE_*`** Secret（见第 4 节）。
4. **（P18.6b）** 在 Cloudflare 创建 **R2 bucket**，配置**公开读**与 **CORS**（见第 5 节）；在 Actions 中配置 R2 写入所需 Secret（命名以仓库 workflow 为准，常见为 S3 兼容的 `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `R2_BUCKET_*` 等）。
5. 在 Pages 项目 **Settings → Build** 中断开 **Git 自动构建**（`Disconnect`），以 **Direct Upload** 为主入口，避免平台 `npm clean-install` 与可选原生依赖（Rolldown 等）与 CI 不一致。
6. 用 **`workflow_dispatch`** 各跑一次 **P18.4 Nightly** 与 **P18.5 Monthly**（或至少 nightly），确认 **Deploy to Cloudflare Pages** 步骤绿、CF 控制台出现新 **Production** 部署；并确认 **大 JSON 从 R2 URL 可被浏览器拉取**（见第 8 节）。
7. （可选）绑定 **自定义域名**：在 Pages 项目里添加域名并完成 DNS；同时核对 **前端 `base` 路径**（见第 6 节）。R2 若使用自定义域，需在 R2 桶的 **Custom Domains** 中单独绑定。
8. **灰度 1–2 周**：保留 **`Deploy GitHub Pages`**（`.github/workflows/deploy-pages.yml`，`main` push 仍会发布到 GitHub Pages），观察 CF 延迟与流量后再决定是否以 CF 为主入口。
9. **国内访问、备案、大陆 CDN** 等不在 P18.6 范围（规划为 Phase 19+）。

## 2. Cloudflare：新建 Pages 项目

1. 登录 [Cloudflare Dashboard](https://dash.cloudflare.com/) → **Workers & Pages** → **Create** → **Pages**。
2. 生产站点由 **GitHub Actions Direct Upload** 推送，因此不必把「连接 GitHub 自动构建」当作唯一来源；若控制台要求选 Git，可后续以 **Upload** / **Direct Upload** 为主，或在项目设置里 **Disconnect** Git，避免与 CI 冲突。
3. **Build 设置（推荐 Direct Upload 主链路）**：若你已采用本仓库 nightly/monthly 的 `pages-action` 直传，建议把 Cloudflare Pages 的 **Production branch / Git 触发构建关闭**（或 **Disconnect**），避免平台侧 `npm clean-install` 与 optional native deps 差异导致误报失败。  
   只有在你明确要启用「Cloudflare 从 Git 构建」时，才配置 Build command（建议与仓库 CI 策略一致，避免裸 `npm ci`）。**注意**：若 Git 构建把 **`galaxy_data.json.gz` > 25 MiB** 打进输出目录，Pages 会在校验阶段直接失败，此时应走 **第 5 节 R2**，不要把该大文件作为 Pages 静态资源发布。
4. 记下：
   - **Account ID**：Overview 右侧 **API** 区域，或 URL `https://dash.cloudflare.com/<account_id>/...` 中的段。
   - **Project name**：创建时填写的项目名称（与 `CLOUDFLARE_PAGES_PROJECT_NAME` **完全一致**，区分大小写）。

## 3. API Token（Cloudflare）

1. **My Profile** → **API Tokens** → **Create Token** → **Create Custom Token**。
2. **Permissions**（最小常用组合）：
   - **Account** → **Cloudflare Pages** → **Edit**
3. **Account Resources**：包含目标账号即可。
4. 创建后复制 token，到 GitHub 设为 **`CLOUDFLARE_API_TOKEN`**（**勿**写入仓库、勿发聊天明文）。

若部署报权限错误，可在排错阶段临时放宽为 **Account → Cloudflare Pages → Edit** + **Zone** 相关读权限（仅当你把自定义域名解析也交给同一 token 自动化时才需要；纯 Pages 上传通常 Account 级 Pages Edit 即可）。

**R2 写入**：GHA 若使用 S3 兼容 API，通常使用 **R2 的 S3 API 访问密钥**（在 R2 概览里创建 **API Token** / **Manage R2 API Tokens**），与上文的 Cloudflare Pages API Token **不是同一把钥匙**；分别存入 GitHub Secrets，最小权限各管各桶。

## 4. GitHub Repository Secrets（Pages 必配）

在仓库 **Settings → Secrets and variables → Actions → New repository secret** 添加：

| Secret 名称 | 含义 |
|-------------|------|
| **`CLOUDFLARE_API_TOKEN`** | 第 3 节创建的、具备 **Pages Edit** 的 token。 |
| **`CLOUDFLARE_ACCOUNT_ID`** | Cloudflare Account ID（UUID 形态字符串）。 |
| **`CLOUDFLARE_PAGES_PROJECT_NAME`** | **Pages** 项目名称（与控制台 **Workers & Pages** 下列出的 **Pages** 项目名一致；勿填 Worker-only 项目名）。 |

**未配置或拼写错误**时，workflow 会在 **Deploy to Cloudflare Pages** 失败；Python 与 artifact 若已成功，仍可在 Actions 里下载 **galaxy-export-*** artifact 排查数据。

**常见错误**：`Project not found (8000007)` 多因为 **Secret 里的项目名对应的是 Worker Git 项目而非 Pages**，或 **Account ID 与 Token 所属账号不一致**。请到 Dashboard 确认资源类型为 **Pages** 后再填 Secret。

## 5. Cloudflare R2（P18.6b：大静态数据）

### 5.1 为什么需要 R2

- Cloudflare **Pages** 对部署目录内**单个文件**有 **25 MiB** 硬上限。
- 当前 `galaxy_data.json.gz` 已超过该限制，**不能**作为 Pages 静态资源与 `frontend/dist` 一并上传。
- **R2** 对象存储无该 Pages 打包限制；浏览器通过 **HTTPS GET** 拉取 gzip 即可（需 **CORS** 允许你的站点源）。

定价与用量摘要见官方 [R2 Pricing](https://developers.cloudflare.com/r2/pricing/)：Standard 存储约 **$0.015/GB·月**，出站自 R2 在文档所述路径下**不计 egress 费**；本项目单对象约 tens of MB、日更一次写入，通常易落在免费档内。

### 5.2 控制台操作（推荐顺序）

1. Dashboard → **R2** → **Create bucket**（名称全局唯一，记下 bucket 名）。
2. 在桶设置中启用 **Public access**（**R2.dev subdomain** 或 **Custom domain** 二选一或组合）。记录对外访问的 **基础 URL**（例如 `https://<bucket>.<accountid>.r2.dev` 或自定义域根）。
3. 配置 **CORS**（R2 bucket → **Settings** → **CORS policy**）：至少允许你的 **Pages 站点源**（`https://<project>.pages.dev` 与自定义域）对对象 URL 发 **`GET`**、**`HEAD`**；若需列目录再按需加（一般不需要）。
4. （可选）对象 key 建议带版本或日期，例如 `galaxy/v42/galaxy_data.json.gz`，便于 **immutable 缓存**；再配合一个极小的 **`manifest.json`**（仍可由 Pages 托管或同桶小文件）指向当前 key。

### 5.3 GitHub Actions 侧

- 在 **Actions secrets** 中配置 R2 **S3 兼容 endpoint**、**region**（R2 常用 `auto`）、**access key id**、**secret access key**、**bucket 名** 等；**具体变量名以仓库 `.github/workflows/*.yml` 实现为准**。
- nightly / monthly 在导出 `frontend/public/data/*.json.gz` 后，应由步骤 **上传至 R2**；Pages 部署步骤只上传 **`frontend/dist`**，且其中**不应再包含**超过 25 MiB 的 `galaxy_data.json.gz`（实施时可通过构建前移除 public 大文件或改为外链 URL）。

### 5.4 前端加载 URL

- **当前默认行为**（未接 R2 前）：前端从 **站点同源** `BASE_URL + data/galaxy_data.json.gz` 加载（见 `frontend/src/utils/loadGalaxyData.ts`）。
- **接 R2 后**：应改为从 **R2 绝对 URL**（或 manifest 给出的 URL）加载；实现方式由 P18.6b PR 统一（例如构建时 `VITE_*` 注入或运行时 manifest）。接好后再做第 8 节验收。

## 6. 自定义域名与前端 `base` 路径

- 当前 Vite 配置里 **`base`** 为 **`/chronicle_v3_3d_galaxy/`**（见 `frontend/vite.config.ts`），与 **GitHub Pages 子路径**一致。
- 若自定义域名指向 **站点根路径**（`https://movies.example.com/`），需二选一（不在本指南替你改代码，仅列决策）：
  - **A**：将 **`base`** 改为 **`/`** 并重新发布（需与现有 GH Pages 书签/外链策略一致）；或  
  - **B**：在 Cloudflare **Workers / Redirect Rules / URL 重写** 把根路径请求重写到 **`/chronicle_v3_3d_galaxy/`** 前缀（实现细节依你的 DNS/Zone 而定）。

切域名后务必做一次 **硬刷新** 与 **无缓存隐私窗口** 验证，避免旧 `index.html` 缓存。

## 8. 验收建议

| 检查项 | 做法 |
|--------|------|
| **Direct Upload 成功** | Actions 中 nightly 或 monthly run 的 **Deploy to Cloudflare Pages** 为绿色；CF 控制台该 **Pages** 项目的 **Deployments** 出现对应时间与 commit。 |
| **大 JSON 走 R2** | 浏览器开发者工具 **Network**：`galaxy_data.json.gz`（或 manifest 指向的 URL）请求为 **200**，**Request URL** 的 host 为 **R2 公开域**（`*.r2.dev` 或自定义域），而非仅 `*.pages.dev` 同源路径（接好 P18.6b 后）。 |
| **数据契约** | 解压/解析后 `meta.version` 带 **`daily`** 或 **`monthly`** 等分支语义（与导出脚本一致）。 |
| **CORS** | 控制台无 `blocked by CORS policy`；若有问题，回到第 5.2 节检查 Allowed origins / Methods。 |
| **与锚点软闸** | monthly 在 **soft** 模式下即使日志里 `anchor_*` 偏大，只要 job 未失败，**仍应执行**构建与部署。 |
| **Artifact** | monthly 仍上传 **`monthly_refit_meta.json`** 与导出文件，可与 CF 部署时间交叉对照。 |

## 9. 排错摘要

| 现象 | 可能原因 |
|------|-----------|
| **Invalid project name** / **Project not found (8000007)** | `CLOUDFLARE_PAGES_PROJECT_NAME` 与 **Pages** 项目名不一致；或误填 **Worker** 项目；或 **Account ID** 与 token 账号不一致。 |
| **Authentication error** | Token 过期、复制少了字符、或权限未包含 **Pages Edit**。 |
| **Build 在 CI 失败** | 多为 Linux 下 optional native 依赖；workflow 已采用与 `deploy-pages.yml` 相同的 **删 lock + `npm install --include=optional`**；若仍失败，对照 **`deploy-pages.yml`** 本地用 WSL/Linux 复现。 |
| **Pages only supports files up to 25 MiB** | `galaxy_data.json.gz` 仍被打进 **Pages 部署目录**；应走 **第 5 节 R2**，并从 `frontend/dist` 发布包中排除该大文件。 |
| **站点白屏 / 资源 404** | **`base`** 与真实 URL 路径不一致（见第 6 节）；或 R2 对象 key / 公开读未配置。 |
| **CORS error** | R2 CORS 未包含当前 **Pages / 自定义域** 源，或用了错误的 scheme（`http` vs `https`）。 |

## 10. 维护说明（可选）

- **`cloudflare/pages-action`** 官方已标记 **deprecated**，长期可迁到 **`wrangler-action`** 的 Pages 部署路径；当前仓库为计划可复现性固定 **`@v1.5.0`**。
- 若将来改为仅 **本地上传产物** 的轻量 job，仍可保留「构建 `frontend/dist` + 同一 `directory`」模式，仅替换触发条件与数据来源。

# P18.6 Cloudflare Pages 切换操作指南

本指南说明 **Phase 18.6** 落地后，你在 **Cloudflare 控制台、DNS、GitHub Secrets** 侧需要完成的配置与验收顺序。代码侧已在 `.github/workflows/nightly_vote_refresh.yml` 与 `.github/workflows/monthly_refit.yml` 末尾接入 **Direct Upload** 部署（`cloudflare/pages-action@v1.5.0`）；Cron 在写出 `frontend/public/data/*` 后会 **安装依赖并 `npm run build -w frontend`**，再把 **`frontend/dist`** 上传到指定 Pages 项目。总体规划见 `.cursor/plans/phase_18_data_infrastructure_9ccb7a3f.plan.md` 中 **P18.6** 小节。

**建议先读完**：

- [P18.4 每日投票刷新与导出入口指南](./P18.4%20每日投票刷新与导出入口指南.md)（nightly、导出、`GALAXY_EXPORT_SEQ`）
- [P18.5 月度星系 refit 操作指南](./P18.5%20月度星系%20refit%20操作指南.md)（月度、四件套、`monthly_refit_meta.json` artifact）

**与 P18.5b 的关系**：部署步骤在 Python job **全部成功**之后执行；锚点 **软闸** 不会单独阻止上传 Pages（硬闸/脚本失败导致 job 失败时自然不会部署）。

---

## 1. 你要完成的待办清单（推荐顺序）

1. 在 Cloudflare 创建 **Pages** 项目，并记下 **Account ID**、**项目名称**（与下面 Secret 一致）。
2. 创建 **API Token**（权限见第 3 节），写入 GitHub Secret **`CLOUDFLARE_API_TOKEN`**。
3. 在 GitHub 仓库 **Settings → Secrets and variables → Actions** 中补齐三个 **`CLOUDFLARE_*`** Secret（见第 4 节）。
4. 用 **`workflow_dispatch`** 各跑一次 **P18.4 Nightly** 与 **P18.5 Monthly**（或至少 nightly），确认 **Deploy to Cloudflare Pages** 步骤绿、CF 控制台出现新 **Production** 部署。
5. （可选）绑定 **自定义域名**：在 Pages 项目里添加域名并完成 DNS；同时核对 **前端 `base` 路径**（见第 5 节）。
6. **灰度 1–2 周**：保留 **`Deploy GitHub Pages`**（`.github/workflows/deploy-pages.yml`，`main` push 仍会发布到 GitHub Pages），观察 CF 延迟与流量后再决定是否以 CF 为主入口。
7. **国内访问、备案、大陆 CDN** 等不在 P18.6 范围（规划为 Phase 19+）。

---

## 2. Cloudflare：新建 Pages 项目

1. 登录 [Cloudflare Dashboard](https://dash.cloudflare.com/) → **Workers & Pages** → **Create** → **Pages**。
2. 生产站点由 **GitHub Actions Direct Upload** 推送，因此不必把「连接 GitHub 自动构建」当作唯一来源；若控制台要求选 Git，可后续以 **Upload** / **Direct Upload** 为主，或在项目设置里关闭与 CI 冲突的自动构建（以你实际 UI 为准）。
3. **Build 设置（推荐 Direct Upload 主链路）**：若你已采用本仓库 nightly/monthly 的 `pages-action` 直传，建议把 Cloudflare Pages 的 **Production branch / Git 触发构建关闭**（或至少不要把它作为主入口），避免平台侧 `npm clean-install` 与 optional native deps 差异导致误报失败。  
   只有在你明确要启用「Cloudflare 从 Git 构建」时，才配置 Build command（建议与仓库 CI 策略一致，避免裸 `npm ci`）。
4. 记下：
   - **Account ID**：Overview 右侧 **API** 区域，或 Pages URL `https://dash.cloudflare.com/<account_id>/pages` 中的段。
   - **Project name**：创建时填写的项目名称（与 `CLOUDFLARE_PAGES_PROJECT_NAME` **完全一致**，区分大小写）。

---

## 3. API Token（Cloudflare）

1. **My Profile** → **API Tokens** → **Create Token** → **Create Custom Token**。
2. **Permissions**（最小常用组合）：
   - **Account** → **Cloudflare Pages** → **Edit**
3. **Account Resources**：包含目标账号即可。
4. 创建后复制 token，到 GitHub 设为 **`CLOUDFLARE_API_TOKEN`**（**勿**写入仓库、勿发聊天明文）。

若部署报权限错误，可在排错阶段临时放宽为 **Account → Cloudflare Pages → Edit** + **Zone** 相关读权限（仅当你把自定义域名解析也交给同一 token 自动化时才需要；纯 Pages 上传通常 Account 级 Pages Edit 即可）。

---

## 4. GitHub Repository Secrets（必配）

在仓库 **Settings → Secrets and variables → Actions → New repository secret** 添加：

| Secret 名称 | 含义 |
|-------------|------|
| **`CLOUDFLARE_API_TOKEN`** | 上节创建的 token。 |
| **`CLOUDFLARE_ACCOUNT_ID`** | Cloudflare Account ID（UUID 形态字符串）。 |
| **`CLOUDFLARE_PAGES_PROJECT_NAME`** | Pages 项目名称（与控制台一致）。 |

**未配置或拼写错误**时，workflow 会在 **Deploy to Cloudflare Pages** 失败；Python 与 artifact 若已成功，仍可在 Actions 里下载 **galaxy-export-*** artifact 排查数据。

---

## 5. 自定义域名与前端 `base` 路径

- 当前 Vite 配置里 **`base`** 为 **`/chronicle_v3_3d_galaxy/`**（见 `frontend/vite.config.ts`），与 **GitHub Pages 子路径**一致。
- 若自定义域名指向 **站点根路径**（`https://movies.example.com/`），需二选一（不在本指南替你改代码，仅列决策）：
  - **A**：将 **`base`** 改为 **`/`** 并重新发布（需与现有 GH Pages 书签/外链策略一致）；或  
  - **B**：在 Cloudflare **Workers / Redirect Rules / URL 重写** 把根路径请求重写到 **`/chronicle_v3_3d_galaxy/`** 前缀（实现细节依你的 DNS/Zone 而定）。

切域名后务必做一次 **硬刷新** 与 **无缓存隐私窗口** 验证，避免旧 `index.html` 缓存。

## 6. 灰度：保留 GitHub Pages

- Workflow **`.github/workflows/deploy-pages.yml`** 仍在 **`push` 到 `main`** 时构建并部署到 **GitHub Pages**。
- P18.6 建议 **1–2 周** 内双轨：对外逐步宣传 CF 域名，GH Pages 作回滚备线；稳定后再决定是否弱化 GH Pages 触发频率（属运营决策，非本 phase 强制代码变更）。

## 7. 验收建议

| 检查项 | 做法 |
|--------|------|
| **Direct Upload 成功** | Actions 中 nightly 或 monthly run 的 **Deploy to Cloudflare Pages** 为绿色；CF 控制台该项目的 **Deployments** 出现对应时间与 commit。 |
| **数据进包** | 打开 CF 上的站点，开发者工具 Network 中确认 **`galaxy_data.json`** / **`.gz`** 请求为 **200**，且 `meta.version` 带 **`daily`** 或 **`monthly`** 分支语义（与导出脚本一致）。 |
| **与锚点软闸** | monthly 在 **soft** 模式下即使日志里 `anchor_*` 偏大，只要 job 未失败，**仍应执行**构建与部署。 |
| **Artifact** | monthly 仍上传 **`monthly_refit_meta.json`** 与导出文件，可与 CF 部署时间交叉对照。 |

## 8. 排错摘要

| 现象 | 可能原因 |
|------|-----------|
| **Invalid project name** | `CLOUDFLARE_PAGES_PROJECT_NAME` 与控制台项目名称不一致。 |
| **Authentication error** | Token 过期、复制少了字符、或权限未包含 **Pages Edit**。 |
| **Build 在 CI 失败** | 多为 Linux 下 optional native 依赖；workflow 已采用与 `deploy-pages.yml` 相同的 **删 lock + `npm install --include=optional`**；若仍失败，对照 **`deploy-pages.yml`** 本地用 WSL/Linux 复现。 |
| **站点白屏 / 资源 404** | **`base`** 与真实 URL 路径不一致（见第 5 节）。 |

## 9. 维护说明（可选）

- **`cloudflare/pages-action`** 官方已标记 **deprecated**，长期可迁到 **`wrangler-action`** 的 Pages 部署路径；当前仓库为计划可复现性固定 **`@v1.5.0`**。
- 若将来改为仅 **本地上传产物** 的轻量 job，仍可保留「构建 `frontend/dist` + 同一 `directory`」模式，仅替换触发条件与数据来源。

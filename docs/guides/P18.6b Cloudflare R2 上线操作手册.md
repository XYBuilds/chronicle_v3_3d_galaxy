# P18.6b Cloudflare R2 上线操作手册

> **Phase 40 现行运维契约**：R2 upload 只发布 galaxy/search assets 和 assets manifest；manifest 不得含 `today_url` 或 Today R2 key。OG Index checkpoint 为 `ops/og-index/state-v2.json.gz`（schema `2`、projection `og-index-v2`），日常 writer 只处理 `movie:{id}` 与 `meta:G`。v1 读取、KV `today` 删除和 Today R2/KV/cache 的远端清理均是 Phase 40.8 人工 Gate，不能由 scheduled 任务自动执行。

> **退役 Today 边界**：`today`（历史 KV key，不可由 scheduled 或回滚流程读取、写入或恢复）、`today.json`、`today_url`、`og-today.png` 及 Today R2/cache 对象只可在明确授权的历史取证中提及；不得按旧指南生成、上传、清理或重新路由。

本手册是给你实际执行的「运营侧清单」：把 `galaxy_data.json.gz` / `galaxy_search_index.json.gz` 从 Pages 包内迁到 R2，保证 nightly/monthly 自动上传，前端通过 manifest 或环境变量读取 R2 URL。

当前仓库代码已接入：

- `scripts/cron/upload_galaxy_r2.py`
- `.github/workflows/nightly_vote_refresh.yml`（包含 `Upload galaxy gzip to R2 (P18.6b)`）
- `.github/workflows/monthly_refit.yml`（包含 `Upload galaxy gzip to R2 (P18.6b)`）
- 前端 URL 解析：`frontend/src/lib/galaxyAssetUrls.ts`

## Phase 40：OG index checkpoint 与 R2 共享凭据

R2 同时保存主 galaxy gzip 和 OG index writer checkpoint，但用途不同：`ops/og-index/state-v2.json.gz` 是不由前端或 Worker 直接消费的已提交同步状态。它采用 schema `2` / projection `og-index-v2`，上传带 `Cache-Control: no-store`。snapshot 缺失或损坏时，增量同步 fail closed，不会自动全量覆盖远端。

两个 workflow 都在计算/export 成功后、常规 R2 galaxy 上传前运行同一个 **Sync OG index KV incrementally** 步骤。它只比较 `title`、`release_date`、`genres`、`poster_url`，并按「影片 PUT → 影片 DELETE → read-back 验证影片变化 → 写入并验证 `meta:G` → snapshot commit」提交。失败保留旧 snapshot，重试会从该 checkpoint 幂等恢复；OG Worker 只消费 `movie:{id}` 与 `meta:G`。

scheduled workflow 只接受已验证的 v2 checkpoint，不会自动 bootstrap 或 full fallback。v1→v2 迁移和遗留 Today 对象删除是独立的 Phase 40.8 人工 Gate，不能作为日常同步或故障回滚。

## 0. 最终你要达成的结果

完成后应满足：

1. nightly/monthly 的 R2 上传步骤均为绿色。
2. 浏览器请求 `galaxy_data.json.gz` 的 host 是 R2 公网域名（不是 Pages 同源 `.../data/galaxy_data.json.gz`）。
3. Cloudflare Pages 部署不再受单文件 25MiB 限制影响（因为构建前已 prune 大文件）。
4. 前端在没有 R2 配置时仍可回退（脚本会 skip，不阻塞流程）。

## 1. Cloudflare R2 控制台一次性配置

### 1.1 创建 bucket

在 Cloudflare Dashboard → **R2**：

- 创建一个 bucket（例如 `chronicle-galaxy-prod`）。
- 记下 bucket 名，后面填到 GitHub Secret `R2_BUCKET`。

### 1.2 配置公网访问

你可以二选一：

- `*.r2.dev` 公网子域（最快）
- 自定义域（更可控）

把最终的公网基地址填到 Secret `R2_PUBLIC_BASE_URL`，示例：

- `https://pub-xxxxxxxx.r2.dev`
- `https://assets.your-domain.com`

注意：这个值要填「域名基址」，不带对象 key，末尾有无 `/` 都可以（脚本会处理）。

### 1.3 配置 CORS

在 bucket 的 CORS policy 中至少允许：

- Origins：你的 Pages 域名（例如 `https://<project>.pages.dev`）+ 生产自定义域名
- Methods：`GET`, `HEAD`
- Headers：默认即可（如需可加 `*`）

如果你要本地验证 R2 拉取，再临时加：

- `http://127.0.0.1:4173`

## 2. GitHub Secrets（必须）

仓库路径：**Settings → Secrets and variables → Actions**。

新增/确认以下 Secrets：

- `R2_ACCOUNT_ID`
- `R2_ACCESS_KEY_ID`
- `R2_SECRET_ACCESS_KEY`
- `R2_BUCKET`
- `R2_PUBLIC_BASE_URL`

说明：

- 这 5 个变量在 workflow 里传给 `upload_galaxy_r2.py`。
- 脚本是「全有才启用」：缺任意一个会打印 skip 并返回 0，不会让 job 失败。
- Pages 相关的 `CLOUDFLARE_*` 仍然需要保留（部署 `frontend/dist` 用）。

## 3. R2 API Token 权限建议（最小权限）

在 Cloudflare 创建 R2 API 凭据时，建议：

- Scope 仅当前目标 bucket
- 权限至少包含对象写入（Put）和读取（用于验证）
- 不要复用 Pages API token（职责分离）

## 4. 第一次上线验证（建议按这个顺序）

### 4.1 先跑 nightly（workflow_dispatch）

触发 `.github/workflows/nightly_vote_refresh.yml`，重点看三个步骤：

1. `Run nightly vote refresh`
2. `Upload galaxy gzip to R2 (P18.6b)`
3. `Deploy to Cloudflare Pages`

你应在日志中看到类似：

- `[R2] shapes: gal_gz_bytes=... idx_gz_bytes=... version='...'`
- `[R2] upload key='galaxy/galaxy_data.json.gz' ...`
- `[R2] wrote frontend/public/data/galaxy_assets_manifest.json`
- `[R2] prune ...`（因为 workflow 设置了 `R2_GALAXY_PRUNE_AFTER_UPLOAD=1`）

### 4.2 再跑 monthly（workflow_dispatch）

触发 `.github/workflows/monthly_refit.yml`，同样检查上述 R2 步骤。

如果月度软闸模式是 `soft`，只要 monthly 主脚本没 fail，R2 + Pages 仍应继续执行。

## 5. 浏览器端验收（最关键）

打开生产站点，DevTools → Network：

1. 找到 `galaxy_data.json.gz` 请求
2. 看 `Request URL`：
   - 应该是 `R2_PUBLIC_BASE_URL/.../galaxy_data.json.gz?v=<data_version>`
3. Response 状态应是 200，且无 CORS 报错

再检查搜索索引：

- `galaxy_search_index.json.gz` 也应走 R2（若 manifest 提供了 index URL）

## 6. 当前前端 URL 解析优先级（排错必读）

代码在 `frontend/src/lib/galaxyAssetUrls.ts`，优先级如下：

1. `VITE_GALAXY_DATA_GZIP_URL` / `VITE_GALAXY_SEARCH_INDEX_GZIP_URL`
2. `?dataset=...` 实验参数（不会被 manifest 覆盖）
3. `data/galaxy_assets_manifest.json`
4. 同源默认路径（`data/galaxy_data.json.gz` / `data/galaxy_search_index.json.gz`）

这意味着：

- 你要临时强制切某个对象 URL，直接配 `VITE_*` 最快。
- 线上常态建议走 manifest（自动带 `?v=data_version`）。

## 8. 常见故障与处理

### 8.1 R2 step 显示 skip

现象：日志出现 `skip: set R2_ACCOUNT_ID ...`

处理：补齐 5 个 R2 secrets（名称必须完全一致）。

### 8.2 上传时报鉴权错误

处理：

- 检查 `R2_ACCOUNT_ID` 是否与 access key 所属账号一致
- 重建一套 R2 API 凭据并更新 `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY`

### 8.3 浏览器 CORS 报错

处理：

- 回到 bucket CORS，把当前站点域名加到 Allowed origins
- 确认是 `https` 域名，不要只配 `http`

### 8.4 仍然请求 Pages 同源 data 路径

处理顺序：

1. 检查 `galaxy_assets_manifest.json` 是否成功随站点发布
2. manifest JSON 字段是否包含 `galaxy_data_gzip_url`
3. 是否被 `?dataset=` 或 `VITE_*` 覆盖了 URL 解析

---

## 9. 回滚预案（5分钟内可执行）

当 R2 出现故障（域名、CORS、权限）且你要快速恢复：

1. 临时移除/清空 5 个 R2 secrets（或把 workflow 里的 R2 step先注释）
2. 重新跑一次 nightly 或 monthly
3. 脚本会自动 skip，前端回退到同源 `data/*.json.gz`

注意：此回滚会让大文件重新进入 Pages 链路，若 gzip 超 25MiB，可能再次触发 Pages 文件上限问题。  
所以回滚只用于紧急短时，长期仍应修复 R2。

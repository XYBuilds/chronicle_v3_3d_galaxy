# P26.1 HDR 与色彩验证测试指南

本指南对应 Phase **P26.1**（见 `.cursor/plans/phase_26_device_spatial_optimization.plan.md`）：在 **Mac / Windows**、**HDR 开/关**、**多浏览器** 下，系统化对比 **idle / active 星点**、**focus Perlin 球**、**rating reference**、**cover / loading 品牌字**、**drawer / HUD 白边与边框**，并尽量区分偏色来自 **CSS OKLCH token**、**WebGL sRGB 输出**、**系统/浏览器 HDR 色彩管理**，还是 **显示器 / 截图链路**。

结论与矩阵表可归档到：`docs/reports/Phase 26.1 P26.1 HDR 色彩验证矩阵 实施报告.md`。

若开发机只有 Windows、需要在 **Mac 真机 + Safari** 上看色，请直接使用 **第 3 节** 的 SSH 反向隧道步骤。

---

## 1. 本指南回答什么

跑完一次完整矩阵后，应能书面回答：

1. **idle 与 active 的色差**是否在多环境下稳定复现？是否仅在某一种 HDR 或浏览器组合上出现？
2. **DOM（HUD）** 与 **WebGL（星场 / Perlin）** 是否「各走各的」：例如 HUD 与 CSS 色块一致，但星点异常，则更指向 WebGL / 合成链路。
3. **WebGL 中心 `readPixels` 数值** 与肉眼看到的背景/星场是否一致：若读数是预期黑/近黑而屏幕发灰，则更指向显示与色彩管理，而非 shader 写错。
4. 是否需要进入 **改 token / 改 shader** 阶段（P26.1 结论）；本阶段**不**凭单设备主观感受直接改全局色。

## 3. 可选：Windows 跑本地前端，从 Windows SSH 到 Mac，让 Mac 本机浏览器打开测试页

适用场景：**Vite 构建 + preview（或 dev）只在一台 Windows 上跑**，但 P26.1 必须在 **Mac 的 Safari / Chrome + Mac 显示器与 HDR 链路** 上看色。做法是在 Windows 上建立一条 **SSH 反向端口转发（remote forwarding）**：Mac 上访问自己的 `localhost:某个端口`，流量经 SSH 落到 Windows 的 **`127.0.0.1:4173`**（本指南默认；若你用 `vite dev` 一般为 **`5173`**，下文凡出现 `4173` 处请改成你的实际端口）。

> **端口约定**：下文示例统一使用 **`4173`**（`vite preview` 默认端口）。使用 **`npm run dev`** 时通常为 **`5173`**，将 `-R` 与 URL 中的 `4173` 全部替换为 `5173` 即可。

### 3.1 原理（一句话）

在 **Windows** 上执行 `ssh -R …` 登录 **Mac** 时，让 **Mac 的 sshd** 在本机监听一个 TCP 端口，并把该端口上的连接 **转回** Windows，再由 Windows SSH 客户端连到本机 Vite。这样 Mac 上 Safari 打开 `http://127.0.0.1:4173` 等同于访问 Windows 上的前端服务。**`vite dev` 时 HMR WebSocket 也是 TCP，多数环境可一并经隧道工作；`vite preview` 无 HMR。**

### 3.2 Mac 侧准备

1. **打开远程登录（SSH 服务）**  
   - macOS Ventura 及以后：**系统设置 → 通用 → 共享 → 远程登录** → 打开；可限制为当前用户或指定用户。  
   - 记下 Mac 在局域网中的 **主机名或 IP**（例如 `192.168.1.20` 或 `imac.local`）。

2. **防火墙**  
   - 若启用「防火墙」，确认 **允许 `sshd` 入站**（通常打开「远程登录」会自动处理）。

3. **可选：仅密钥登录**  
   - 在 Mac `~/.ssh/authorized_keys` 中放入 Windows 侧公钥，避免每次输密码（与日常 SSH 配置相同，此处不展开）。

### 3.3 Windows 侧准备

1. **已安装 OpenSSH 客户端**（Windows 10/11 自带，默认启用）。在 PowerShell 中执行 `ssh -V` 应能看到版本。

2. **在本机启动前端服务**（仓库根目录示例；**preview 对应端口 4173**）：

```powershell
npm run build -w frontend
npm run preview -w frontend
```

确认浏览器在 **Windows 本机** 访问 `http://127.0.0.1:4173` 正常。默认 `vite preview` 监听 `127.0.0.1:4173` 即可，无需 `--host` 也能配合下文 `-R 127.0.0.1:4173:127.0.0.1:4173`。若你坚持用 **`npm run dev -w frontend`**，请改用 `http://127.0.0.1:5173` 并将下文 `4173` 改为 `5173`。

### 3.4 建立反向隧道（在 Windows PowerShell 执行）

将 `MAC_USER`、`MAC_HOST` 换成你的 Mac 登录名与 IP/主机名：

```powershell
ssh -N -o ServerAliveInterval=30 -o ServerAliveCountMax=3 `
  -R 127.0.0.1:4173:127.0.0.1:4173 MAC_USER@MAC_HOST
```

| 参数 | 含义 |
| --- | --- |
| `-N` | 不执行远程 shell，只做转发（窗口会「挂住」属正常）。 |
| `ServerAliveInterval` | 周期性保活，减少长时间静置断线。 |
| `-R 127.0.0.1:4173:127.0.0.1:4173` | 在 **Mac** 上监听 `127.0.0.1:4173`，转发到 **发起 ssh 的这台 Windows** 的 `127.0.0.1:4173`（即本机 preview）。 |

**若 Mac 本机 4173 已被占用**（例如 Mac 上自己也跑了 `vite preview`），可改用 Mac 侧另一端口，例如 `14173`：

```powershell
ssh -N -o ServerAliveInterval=30 `
  -R 127.0.0.1:14173:127.0.0.1:4173 MAC_USER@MAC_HOST
```

则在 Mac 浏览器地址栏使用：

```text
http://127.0.0.1:14173/?p26ColorAudit=1&todayMovieId=<TMDB_ID>
```

### 3.5 Mac 上打开页面

1. 确认 Windows 上 **上述 `ssh` 命令仍在运行**、且 **preview（或 dev）未退出**。  
2. 在 Mac 打开 **Safari 或 Chrome**，访问：

```text
http://127.0.0.1:4173/?p26ColorAudit=1&todayMovieId=<TMDB_ID>
```

（若用了第 3.4 节的备用端口，把 URL 里的 `4173` 改成 `14173`。）

3. 按第 **6、7** 节继续做 HDR on/off 与截图记录即可。

### 3.6 常见问题

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| Mac 浏览器「无法连接」 | Windows 未开 **preview / dev**、或 `ssh -N` 已断开 | 重开 `npm run preview`（或 `dev`）；重跑 `ssh -R`。 |
| `ssh` 报 `remote port forwarding failed` | Mac 上 4173（或所选 Mac 侧监听端口）已被占用 | 换 Mac 侧监听端口（见 3.4 示例 `14173`）。 |
| `Permission denied (publickey,password)` | 用户/密钥不对 | 检查 `MAC_USER`、密码或 `authorized_keys`。 |
| Mac 能开页但静态资源 404 / 白屏 | 少见；多为构建或路径 | 看 Windows 终端 Vite 日志。 |
| 服务跑在 **WSL2** 里而非 Windows 本机 | `-R` 目标 `127.0.0.1:4173` 指 Windows 环回，未必指到 WSL | **建议** P26.1 隧道场景下在 **Windows 原生** Node 跑 `preview` / `dev`；若必须在 WSL，需在 Windows 侧增加端口转发到 WSL 的监听地址（略复杂，本指南不展开）。 |

### 3.7 安全说明

反向转发把 **Mac 本机可访问的一个端口** 绑到 **你 Windows 上的服务**。本例使用 `127.0.0.1` 绑定在 Mac 侧，**仅本机**可访问，一般不暴露到局域网。请勿在未理解风险的情况下改用 `0.0.0.0` 或把无关服务暴露在 `-R` 目标上。

### 3.8 反向操作：Mac 起服务，想在 Windows 浏览器看

若改为 **Mac 跑 preview / dev、Windows 看色**，应在 **Windows** 上使用 **本地转发 `-L`**（与 `-R` 方向相反），例如（Mac 上服务在 `127.0.0.1:4173` 时）：

```powershell
ssh -N -L 127.0.0.1:4173:127.0.0.1:4173 MAC_USER@MAC_HOST
```

然后在 **Windows** 浏览器打开 `http://127.0.0.1:4173/…`（若 Mac 用 dev 默认端口则改为 `5173`）。本节主场景仍以「Windows 起服务 + Mac 浏览器」为主。

## 5. 内置工具：P26.1 color audit 浮层

在满足 `p26ColorAudit` 且应用进入 **主场景**（数据与索引就绪、Cover 流程已 gate）后，左下角出现浮层，包含：

### 5.1 CSS 变量色块（DOM 侧）

与 `frontend/src/index.css` 中 HUD / 宇宙背景相关 token 对齐，用于判断 **OKLCH + 主题** 在当台显示器上的呈现：

- `--foreground`、`--border`、`--muted-foreground`、`--background`、`--ring`
- `--cosmos-brand-muted`、`--cosmos-universe-bg`
- `--ui-edge-canvas-color`（悬停环 / Timeline 等压在 canvas 上的细线色）

**怎么看**：若 HUD 文字/描边与对应色块 **明显不一致**，先怀疑 **叠加层透明度、backdrop、或截图压缩**；若 **色块之间相对关系** 与 Figma/设计预期不符，再怀疑 **主题或 token**。

### 5.2 纯 sRGB 平面参考

浮层内三个硬编码色块：`#FFFFFF`、`#808080`、`#000000`。

**怎么看**：若 OKLCH 灰阶与 sRGB 参考 **在 HDR on/off 下相对变化不一致**，提示 **色彩管理或 EOTF** 介入；若仅 WebGL 区域异常而 sRGB 块稳定，提示问题更可能在 **WebGL 合成或后处理**。

### 5.3 Sample WebGL center RGBA

点击按钮后，对带 `data-galaxy-webgl="1"` 的主 WebGL2 canvas 执行 **`readPixels`**，采样 **帧缓冲中心** 一个像素（坐标为 WebGL 惯例：**原点在左下**；实现里使用 `floor((w-1)/2)`、`floor((h-1)/2)`）。

**典型预期**

- 宏观 idle、背景以黑为主时，中心常接近 **`#000000` 或极低 RGB**；若 Perlin / 高亮占满中心则读数会非黑，属正常。
- 该读数是 **线性管线写入、按当前输出色彩空间解释后的字节**，工程上约定为 **Three.js `SRGBColorSpace`**（见 `frontend/src/three/scene.ts`）。

**限制（必读）**

- 读的是 **当前默认 FBO** 在点击时刻的内容；若 Bloom / 后处理写入离屏缓冲再合成，读数可能 **不** 等于肉眼最终像素；此时读数仍有助于对比「GPU 出口」与「屏幕」差异。
- 需在 **场景已挂载、canvas 存在** 后再点；否则会提示无 WebGL canvas。
- 不要在 **隐私模式严格限制 WebGL** 的浏览器配置下强依赖该按钮。

### 5.4 `dynamic-range: high` 一行

浮层展示 `matchMedia('(dynamic-range: high)')` 是否匹配。  
这表示浏览器报告的 **高动态范围能力倾向**，**不等于** 操作系统「HDR 显示」开关的权威状态；仍以你在系统设置里记录的 HDR on/off 为准。

## 7. 每一步操作清单（每台机器）

### 7.1 环境登记（1 分钟）

在记事本或报告表格中写下：

- 日期、测试人
- 操作系统版本、浏览器版本
- HDR：开/关；若 macOS 为「参考模式」或 Windows 为「自动 HDR」等子选项，写明
- 显示器：型号、分辨率缩放、内建/外接

### 7.2 打开基准 URL

使用第 3 节 URL，确认：

- 无控制台 **红色** 报错；若有 `[P26.1] today override id not in bundle`，更换 `todayMovieId`。
- 左下角出现 **P26.1 color audit**。

### 7.3 Cover 阶段（固定影片时）

观察 **cover / loading 品牌字**（`--cosmos-brand-muted` 等与浮层色块对照）：

- 与浮层中 `--cosmos-brand-muted`、`--cosmos-universe-bg` 色块对比，记录 **偏暖/偏冷/发灰/发糊** 等主观词 + 是否仅在 HDR on 出现。

### 7.4 进入星系 idle

- **Idle 星点**：整体色调、白点是否发青/发黄；与 sRGB 灰阶块对比亮度感。
- 点击 **Sample WebGL center RGBA**，复制读数到表格。

### 7.5 Hover / active（不进入 focus 也可先做）

- 悬停使某星进入 **active** 高亮，观察与 **idle** 的色差是否符合预期。
- 若怀疑仅 bloom：可对比 **星点核心** vs **光晕边缘**（主观描述即可）。

### 7.6 Focus：Perlin + rating reference

从 cover **Enter** 或从 idle 点选同一影片进入 **focus**：

- **Perlin 球**：高光与暗部是否「洗白」或「压黑」。
- **FocusL rating reference**（若可见）：与浮层 `--foreground` / `--muted-foreground` 对比。
- 再次 **Sample WebGL center**（此时中心可能被球或高光占据），记录读数与画面内容说明（避免误读为「黑场异常」）。

### 7.7 HUD：drawer、搜索条、顶栏

打开 **Info**、**Drawer**、看 **SearchBar** 与右上角图标区：

- 白字/灰字与浮层 token 色块对齐度。
- **细边框**（`--border`、`--ui-edge-canvas-color`）在 HDR on 下是否发糊或过亮。

### 7.8 截图命名建议

便于归档：

```text
P26.1_<OS>_<Browser>_HDR-<on|off>_<scene>-<idle|focus|hud>.png
```

## 9. 简易判定思路（非绝对）

```text
HUD 与 CSS 色块一致，WebGL 区域异常
  → 优先查 WebGL 输出、合成、后处理、与 HDR 下窗口缓冲格式。

HUD 与 CSS 色块已不一致
  → 优先查主题、OKLCH 在当浏览器的计算、以及 OS 级色彩滤镜。

readPixels 合理但肉眼发灰/发绿
  → 优先查显示器、HDR、截图软件色彩描述文件。

仅 Safari 或仅 Chrome
  → 记为「浏览器差异」，避免在另一浏览器上「修假问题」。
```

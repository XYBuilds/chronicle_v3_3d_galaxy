# P34.3 OG Index KV 上线操作指南

本指南是 **Phase 34.3** 的运维侧清单：把社交预览所需的**影片元数据索引**写入 Cloudflare KV（`OG_INDEX` namespace），并**停用** nightly 静态 `og-today.png` 管线。

**背景与计划 SSOT**：`.cursor/plans/phase_34_social_preview_distribution.plan.md` §34.3；当前发布协议以 Phase 38 的 `.cursor/plans/phase_38_og_index_kv_incremental_sync_2e86753a.plan.md` 为准。
**前置阅读**（Cloudflare 账号与 CI 已具备时）：

- [P18.6 Cloudflare Pages 切换操作指南](./P18.6%20Cloudflare%20Pages%20切换操作指南.md) — `CLOUDFLARE_ACCOUNT_ID` / `CLOUDFLARE_API_TOKEN`
- [P18.6b Cloudflare R2 上线操作手册](./P18.6b%20Cloudflare%20R2%20上线操作手册.md) — nightly/monthly 主链路顺序
- [P34.2 静态 OG 基线审计](../reports/Phase%2034.2%20P34.2%20静态%20OG%20基线审计%20实施报告.md)（可选）— 切换前现状

## Phase 38 当前同步协议（优先于下文旧 Phase 34 操作说明）

- `movie:{id}` 只由 `title`、`release_date`、`genres`、`poster_url` 的规范化 JSON 决定；评分、热度、坐标和其他导出字段变化不会写影片键。Worker 的 `movie:{id}`、`today`、`meta:G` 键契约不变。
- 写入方的已提交检查点是 R2 的 `ops/og-index/state-v1.json.gz`。它是 schema `1`、projection `og-index-v1` 的 gzip JSON，上传设为 `Cache-Control: no-store`；不存在或校验失败均 **fail closed**，scheduled run 不删除、不全量回退。
- 正常同步的严格顺序是：影片 PUT → 影片 DELETE → 变化的 `today` → 最后的 `meta:G` → 读回变化/删除键 → 覆盖 R2 snapshot。任一失败都保留旧 snapshot；下一次从旧 checkpoint 幂等重放。
- 默认门槛为 `OG_INDEX_MAX_PUTS=900`、`OG_INDEX_MAX_DELETES=900`。PUT 包含 `today` / `meta:G` 控制键；超过任一门槛会在首笔写入前失败，并输出机器可读的数量、批次和 sample keys。
- 首次没有 snapshot 时，只能在一次性 **`workflow_dispatch`** 中勾选 `bootstrap_og_index`，执行只读 remote audit 后按同一增量顺序修正并提交首个 checkpoint。scheduled nightly/monthly 不会自动 bootstrap 或 full fallback。
- `--scope full --allow-full-recovery` 是灾难恢复路径：需两个显式授权，读取并验证最终远端 keyset 后才提交 snapshot；不是 snapshot 缺失/损坏的自动修复手段。

**与 P23.5 的关系**：P23.5 的 `render_og_today.py` → `og-today.png` 在 **34.3 起不再被 nightly/monthly 调用**，也不再上传 R2。脚本仍保留在仓库内供回滚；社交图 PNG 改由 **Phase 34.4 Worker** 动态生成（本指南只负责 **KV 索引**，不负责 Worker 部署）。

## 1. KV 里存什么（键约定）

Worker（34.4）与主仓脚本共用下列约定：

| Key | 值类型 | 内容 |
|-----|--------|------|
| `meta:G` | 纯字符串 | `galaxy_data.json` → `meta.version`（与 R2 manifest `data_version` 对齐，如 `2026.05.10.daily.30`） |
| `today` | JSON 对象 | `{"date":"YYYY-MM-DD","movie_id":number}`，来自 `frontend/public/data/today.json` |
| `movie:{id}` | JSON 对象 | `{"title","release_date","genres","poster_url"}` — 仅 OG 所需最小字段 |

**不写入 KV 的内容**：overview、多语言 HUD 文案、`lang` query、`vote_count` 等（见 Phase 34 计划 §内容身份）。

**同步范围（Phase 38 脚本行为）**：nightly 与 monthly 都只负责计算/export；它们各自在 workflow 中共享同一个 **Sync OG index KV incrementally** 独立步骤。该步骤固定运行 `--scope incremental`，在常规 R2 上传及 Pages 部署之前执行。只有 `workflow_dispatch` 的 `bootstrap_og_index=true` 会附加 `--bootstrap-remote-audit`；scheduled 不会走 bootstrap、daily 或 full scope。

> **重要**：不要再运行旧的 `daily` scope 或把 monthly 当作常规 `full`。若 checkpoint 缺失，先人工确认远端状态，再从 Actions 的 `workflow_dispatch` 执行一次 remote-audit bootstrap。

## 2. Cloudflare 控制台：创建 KV namespace

1. 登录 [Cloudflare Dashboard](https://dash.cloudflare.com/) → 选择 **The Movie Cosmos** 使用的同一 Account。
2. 左侧 **Workers & Pages** → **KV**。
3. **Create a namespace**：
   - 显示名称建议：**`OG_INDEX`**（仅便于人类识别；绑定 Worker 时用 **Namespace ID**，不是显示名）。
4. 创建后打开该 namespace → 复制 **Namespace ID**（UUID 形态）。

**暂不需要**在 Pages 项目里绑定 KV；绑定发生在 **34.4 独立 Worker 仓库** 的 `wrangler.toml`（`[[kv_namespaces]] binding = "OG_INDEX"`）。主仓只通过 **REST API bulk put** 写数据。

可与 Pages 部署共用 **`CLOUDFLARE_API_TOKEN`**，也可单独建 Token（职责分离更稳妥）。

## 4. GitHub Actions Secrets

路径：**仓库 Settings → Secrets and variables → Actions → Repository secrets**。

### 4.1 必填（启用 KV 同步）

| Secret | 说明 |
|--------|------|
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare account ID |
| `OG_INDEX_KV_NAMESPACE_ID` | §2 复制的 Namespace ID |
| `OG_INDEX_KV_API_TOKEN` | 建议专用、具备 Workers KV Storage Edit 的 Bearer token |
| `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` / `R2_BUCKET` | 同步 checkpoint 的 R2 凭据；与 P18.6b 主对象上传共用 |

**启用逻辑**：这些变量是独立 incremental step 的必需凭据。缺任意一个会使该步骤 fail closed，阻止后续常规 R2 / Pages 发布；不会 `skip`，也不会退化为 full sync。CLI 本地可在没有 `OG_INDEX_KV_API_TOKEN` 时回退到共享 `CLOUDFLARE_API_TOKEN`，但 workflow 使用专用 token。

### 4.2 配额与可调变量

| 变量 | 默认 | 用途 |
|------|------|------|
| `OG_INDEX_MAX_PUTS` | `900` | movie PUT 加 `today` / `meta:G` 的总写入上限；首笔写入前检查。 |
| `OG_INDEX_MAX_DELETES` | `900` | movie DELETE 上限；与 PUT 独立计数。 |
| `OG_INDEX_KV_BATCH_SIZE` | `1000` | bulk 每批键数（最大 `10000`）。 |

`--allow-over-quota` 只限人工 CLI；scheduled workflow 不设置它。

### 4.3 本地 `.env`（仓库根目录，勿提交）

可复制 `.env.example` 中 P34.3 段：

```env
CLOUDFLARE_ACCOUNT_ID=your_account_id
OG_INDEX_KV_NAMESPACE_ID=your_namespace_uuid
# Prefer a dedicated KV token; the shared CLOUDFLARE_API_TOKEN is the fallback.
OG_INDEX_KV_API_TOKEN=your_kv_api_token
# OG_INDEX_MAX_PUTS=900
# OG_INDEX_MAX_DELETES=900
# OG_INDEX_KV_BATCH_SIZE=1000
```

## 5. 一次性：remote-audit bootstrap（必做）

首次 production 切换前，确认 `galaxy_data.json` 与 `today.json` 已由本次 workflow export。然后从 **Actions → P18.4 Nightly vote refresh 或 P18.5 Monthly galaxy refit → Run workflow**，只在这一次将 `bootstrap_og_index` 勾为 `true`。它先分页读取并复算远端 `movie:*` 的 OG projection hash；只有差异通过配额，才执行正常增量协议并提交首个 R2 snapshot。

不要把缺 snapshot 当作自动 full sync，也不要在 scheduled 中设置 bootstrap。R2 snapshot 存在时 bootstrap 会失败，防止无意重审或覆盖已提交状态。

### 5.1 远端审计所需输入

- `frontend/public/data/galaxy_data.json` — 完整导出（体积大，勿在聊天里粘贴内容）
- `frontend/public/data/today.json` — nightly `pick_movie_today` 产物

若本地没有 galaxy 导出，可先跑 export 或从 Actions artifact 解压上述两文件到同一路径。

### 5.2 仅灾难恢复：人工 full recovery

这不是初始 bootstrap 或日常路径。只有明确认定远端 keyspace 需整体重建时，才可在人工终端执行；两个 flag 缺任何一个都会被拒绝：

```powershell
$env:CLOUDFLARE_ACCOUNT_ID = "..."
$env:CLOUDFLARE_API_TOKEN = "..."
$env:OG_INDEX_KV_NAMESPACE_ID = "..."
python scripts/cron/sync_og_index_kv.py --scope full --allow-full-recovery
```

**bash**：

```bash
export CLOUDFLARE_ACCOUNT_ID=...
export CLOUDFLARE_API_TOKEN=...
export OG_INDEX_KV_NAMESPACE_ID=...
python scripts/cron/sync_og_index_kv.py --scope full --allow-full-recovery
```

### 5.3 预期日志

```text
OG_INDEX_SUMMARY {"bootstrap":false,"current":...,"delete":...,"dry_run":false,"movie_put":...,"total_put":...}
```

full recovery 还会在 read-back 后列出远端 movie keyset 校验；校验失败不会提交 R2 snapshot。

### 5.4 控制台抽查

Cloudflare → KV → **OG_INDEX** → 浏览键：

- 存在 `meta:G`、`today`
- 随机打开 `movie:301334`（或你 `today.json` 里的 `movie_id`），JSON 含 `title` / `poster_url`

**远端审计规模与限额**：bootstrap 会分页列出并读取约 6 万个远端 `movie:*` 键，但只 PUT/DELETE 审计后确认的 delta。若审计读取遇到 API 限流，稍后重跑同一个 bootstrap；若 delta 超过配额门槛，停止并调查远端漂移，不得改用 full 覆盖。

## 6. 日常：nightly / monthly 共享增量发布步骤

无需把 KV 逻辑加回计算脚本。两条 workflow 都在 export/validate/`today.json` 后运行独立的 `Sync OG index KV incrementally`，随后才上传常规 R2 galaxy 对象、构建前端和 Pages 部署。这个步骤固定 `--scope incremental`；每次输出 `OG_INDEX_SUMMARY`，并在任何 checkpoint、配额、KV 或 read-back 异常时阻断发布，而非 skip。

**推荐 CI 顺序**（与 R2 手册一致）：

```text
export galaxy → validate → today.json → [og_index KV] → upload R2 → build frontend → pages deploy
```

### 6.1 验证 workflow_dispatch

1. 正常增量：保持 `bootstrap_og_index=false`，日志应有 `OG_INDEX_SUMMARY`，且只列真实 movie/control 差异。
2. 首次切换：只将 `bootstrap_og_index=true` 使用一次。日志的 `bootstrap=true` 和 `audit_read` 记录是远端只读审计的证据；审计或配额失败时没有 KV mutation。
3. scheduled：没有该输入的自动授权；snapshot 缺失或损坏必须失败，待人工执行上述 bootstrap 或经审批的 disaster recovery。
4. **Upload galaxy gzip to R2** 仍不应出现 `og-today.png` / `og_today_url`，artifact 也不应包含该静态图。

### 6.2 验证 monthly

与 nightly 相同：它使用同一 incremental step，而不是重写全量 `movie:*`。

## 10. 故障排查

| 现象 | 可能原因 | 处理 |
|------|----------|------|
| `OG_INDEX_*` / R2 凭据缺失 | 独立同步步骤无法建立安全发布边界 | 补全 §4.1 所列 KV 与 R2 secrets；步骤会 fail closed。 |
| `KV bulk PUT HTTP 403` | Token 无 KV Edit | 换 Token 或加权限 |
| `KV bulk PUT HTTP 404` | Namespace ID 错误或账号不一致 | 核对 ID 与 Account |
| `missing galaxy_data.json` | 未 export 或路径错 | 先跑 export / 指对 `--public-data-dir` |
| `movies must be non-empty` | galaxy 损坏或空导出 | 跑 `validate_galaxy_json.py` |
| `R2 snapshot missing` | 尚未执行首次 bootstrap | 人工在 `workflow_dispatch` 勾选一次 `bootstrap_og_index`；scheduled 不自动修复。 |
| `R2 snapshot schema invalid` | checkpoint 损坏或版本不兼容 | 停止 scheduled，人工审查后选择 bootstrap（仅缺失）或双授权 disaster recovery。 |
| `OG_INDEX_QUOTA_EXCEEDED` | 差异加控制键超过默认门槛 | 审查 summary；仅人工 CLI 可用 `--allow-over-quota`。 |
| 社交预览仍显示旧 `og-today.png` | 平台缓存 + 前端未切 Worker URL | 等 34.6；Facebook Debugger 重抓 |

## 11. 回滚（紧急恢复静态 OG 图）

若 Worker 未就绪且必须恢复 P23.5 行为：

1. 在 `nightly_vote_refresh.py` / `monthly_refit.py` 中**临时恢复**对 `render_og_today_after_galaxy_export` 的调用（或单独手动跑 `python scripts/cron/render_og_today.py`）。
2. 恢复 `upload_galaxy_r2.py` 对 `og-today.png` 的上传与 manifest 字段（需从 git 历史还原相关片段）。
3. 重新触发 nightly，确认 artifact 含 `og-today.png` 且 R2 manifest 含 `og_today_url`。

回滚后 KV 数据可保留（无害）；恢复 Worker 后按 committed snapshot 继续增量同步。若远端 keyspace 确需重建，按 §5 的双授权 disaster recovery 操作。

# Independent managed Git, Issue, and CI hosts

**Research date:** 2026-08-17  
**Scope:** Managed SaaS only. This comparison evaluates GitLab.com, Codeberg, Bitbucket Cloud, and the one materially stronger additional candidate, Azure DevOps Services, for Chronicle, OG Worker, and Daily Stargazing. Prices are public USD prices before tax and may change.  
**Related ticket:** `docs/wayfinder/github-account-outage-recovery/tickets/compare-independent-development-hosts.md`

## Recommendation

Use the following two-candidate shortlist:

1. **GitLab.com is the recommended primary trial and the only complete fit.** Start on Free in one private top-level group containing the three projects. It combines private/public Git, labels and work-item hierarchy, scheduled hosted CI, artifacts/caches/protected variables, rich project export, APIs/CLI, and—uniquely among the viable candidates here—managed outbound push mirroring on the Free tier. Free includes five users in a private top-level group, 400 compute minutes per month, and 10 GiB project storage; extra compute is currently $10 per 1,000 minutes as a one-time purchase. [GitLab pricing](https://about.gitlab.com/pricing/), [Free namespace limits](https://docs.gitlab.com/user/free_user_limit/), [repository mirroring](https://docs.gitlab.com/user/project/repository/mirror/)
2. **Azure DevOps Services is the private-only contingency.** Its free private-project offer is materially stronger for hosted CI—five Basic users, unlimited private Git repositories, Boards, one Microsoft-hosted parallel job with 1,800 minutes per month, Windows/Linux/macOS images, and pipeline artifacts/caches—but new organizations can no longer enable public projects and all existing public projects are scheduled to become private in 2027. It should be chosen only if GitLab fails the mainland-China connectivity test or its GitLab-specific CI migration is materially harder. [Azure DevOps free limits](https://learn.microsoft.com/en-us/azure/devops/organizations/billing/billing-faq?view=azure-devops), [hosted agents](https://learn.microsoft.com/en-us/azure/devops/pipelines/agents/hosted?view=azure-devops), [public-project retirement](https://learn.microsoft.com/en-us/azure/devops/organizations/projects/about-projects?view=azure-devops)

Do **not** shortlist Codeberg or Bitbucket Cloud as the unified recovery control plane:

- Codeberg's mission and resource policy do not fit three initially private product repositories. It says private/non-promoted content should remain below 100 MiB without an exception, recommends another host when the user does not contribute to free software, and does not sell exceptions. Chronicle's current local Git object store alone reports roughly 1.58 GiB across loose and packed objects before any migration-specific repacking. Codeberg CI also requires volunteer approval, is provided as-is, and offers only `linux/amd64`. [Codeberg FAQ and resource policy](https://docs.codeberg.org/getting-started/faq/), [Codeberg CI caveats](https://docs.codeberg.org/ci/)
- Bitbucket Cloud's own documentation calls its built-in tracker “light weight,” and its current Atlassian-Administration workspaces do not support the built-in Issue Tracker or wiki at all. The Free plan has only 50 hosted build minutes per month, and there is no current managed outbound repository-mirror feature comparable to GitLab's push mirror. Using Jira plus a paid Pipelines plan would defeat the stated preference for one simple, low-cost control plane. [Issue tracker limitations](https://support.atlassian.com/bitbucket-cloud/docs/configure-defaults-for-issue-fields/), [Atlassian Administration workspace limitation](https://support.atlassian.com/bitbucket-cloud/docs/what-is-a-workspace/), [Bitbucket pricing](https://www.atlassian.com/software/bitbucket/pricing?tab=cloud-tab), [deprecated Smart Mirroring](https://support.atlassian.com/bitbucket-cloud/docs/work-with-bitbucket-smart-mirroring/)

This is a platform recommendation, not authorization to create accounts, push code, upload secrets, or change production. The eventual selection should follow a small, secret-free acceptance trial described below.

## Project-specific constraints

- The control plane must begin private but remain capable of becoming public after history and secret checks.
- Normal Daily and Monthly jobs need hosted schedules. The Windows workstation remains an emergency path, not the regular runner.
- Chronicle currently has daily and monthly cron workflows plus manual Site Release, Supabase preflight, and Production Recovery workflows. The checked Chronicle workflows all target `ubuntu-24.04`, so a hosted Windows runner is useful flexibility but not a current selection requirement.
- Chronicle's local `git count-objects -vH` reported 891.08 MiB of loose objects and 692.19 MiB packed (about 1.58 GiB on disk). A hosted repository will normally repack differently, and the full preservation archive is not the same thing as the promoted branches/tags that should be pushed, so this is a capacity signal rather than a predicted hosted bill.
- A daily job consumes about 30 runs per month before push/merge, Site Release, Monthly, preflight, and recovery runs. Therefore 400 GitLab minutes permits at most about 13 minutes per daily run if nothing else ran; 50 Bitbucket minutes permits under two minutes. Actual run measurements, not this ceiling calculation, must decide the compute purchase.
- Git, Issues, CI configuration, artifacts, and secrets have different portability boundaries. No forge export is a complete backup of all of them.

## Verified portability boundaries

### Git repositories

All four are ordinary Git hosts, so promoted branches and tags can be cloned/fetched and stored as a bare mirror or bundle independently of the provider. This does **not** preserve stash, reflogs, unreachable objects, Codex refs, hosted pull/merge requests, settings, CI variables, or artifacts. Those local-only objects belong in the separate full recovery snapshot, not in an ordinary forge migration.

GitLab has the strongest ongoing copy path: Free-tier push mirrors automatically copy branches, tags, and commits to an external repository and can be managed through the REST API or `glab`. GitLab pull mirroring is Premium, but pull mirroring is not needed when GitLab is the primary. [Repository mirroring](https://docs.gitlab.com/user/project/repository/mirror/)

Azure DevOps documents one-time import and a later local two-remote synchronization procedure, not an account-independent managed outbound mirror. Codeberg explicitly tells users to mirror manually. Bitbucket's old Smart Mirroring is not a second SaaS copy and is deprecated for new installations. Therefore only GitLab meets the push-mirror requirement without making a workstation or CI job the mirror scheduler.

### Issues and planning metadata

- GitLab can export a portable project archive containing repositories, Issues, comments, merge requests, labels, milestones, issue boards, and inactive pipeline schedules. It also offers Issue CSV with parent ID/IID fields. However, the project export explicitly omits links between Issues/linked items, CI/CD variables, artifacts, webhooks, encrypted tokens, and pipeline-schedule variables. GitLab itself says project exports are not backups. [Project export](https://docs.gitlab.com/user/project/settings/import_export/), [Issue CSV](https://docs.gitlab.com/user/project/issues/csv_export/)
- Azure Boards has native CSV export/import, including a parent/child import representation, and comprehensive work-item REST APIs. CSV does not preserve every discussion, attachment, history event, or non-parent link; those require API extraction. [CSV import/export](https://learn.microsoft.com/en-us/azure/devops/boards/queries/import-work-items-from-csv?view=azure-devops), [Work Items API](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items?view=azure-devops-rest-7.1)
- Codeberg can migrate repository metadata such as Issues, labels, wiki, releases, and milestones between supported forges, including migration away to another Gitea/Forgejo instance. A provider-neutral Issue archive still requires the Forgejo API or a separately maintained Markdown/JSON export. [Codeberg migration](https://docs.codeberg.org/advanced/migrating-repos/), [Forgejo token/API scopes](https://forgejo.org/docs/latest/user/token-scope/)
- Bitbucket has a notably complete ZIP Issue export/import format containing Issues, comments, attachments, logs, components, milestones, and versions, and exposes the process via REST. Its portability is better than its tracker model: the tracker still lacks the labels and parent/blocker relationships required by this workflow. [Issue export/import](https://support.atlassian.com/bitbucket-cloud/docs/export-or-import-issue-data/), [export format](https://support.atlassian.com/bitbucket-cloud/docs/issue-import-and-export-data-format/)

The later portable-workflow decision should therefore keep stable ticket IDs, `parent`, and `blocked_by` in Markdown-visible Issue bodies or repository files even on GitLab. Native relationships improve the UI but are not the sole authority. This avoids both GitLab Premium lock-in for blockers and the documented loss of links in GitLab project exports.

### CI state and secrets

No candidate's project/repository export is a secrets backup. GitLab explicitly excludes CI/CD variables, encrypted tokens, job artifacts, webhooks, and pipeline-schedule variables from project export. Azure, Codeberg/Woodpecker, and Bitbucket likewise treat saved secret values as runtime configuration rather than portable repository content. The chosen password manager must remain the human authority; the forge receives only scoped deployment copies.

Long-lived release artifacts should remain in the project's existing R2/Cloudflare publication design. Forge job artifacts and caches are transient execution aids: GitLab.com defaults artifacts to 30 days and hosted-runner caches not updated for 14 days are removed; Bitbucket artifacts expire after 14 days; Azure pipeline artifacts are deleted with their pipeline run; Codeberg's Woodpecker path needs external object storage for durability. [GitLab.com limits](https://docs.gitlab.com/user/gitlab_com/), [GitLab hosted cache](https://docs.gitlab.com/ci/runners/hosted_runners/), [Bitbucket artifacts](https://support.atlassian.com/bitbucket-cloud/docs/use-artifacts-in-steps/), [Azure pipeline artifacts](https://learn.microsoft.com/en-us/azure/devops/pipelines/artifacts/pipeline-artifacts?view=azure-devops), [Woodpecker S3 plugin](https://woodpecker-ci.org/plugins/s3)

## Mainland-China operating caveat

No first-party source reviewed promises reliable access, latency, or an availability SLA specifically from mainland China for any candidate. It would be unsafe to convert server geography into a claim that a service is reachable through every local network. What the providers do publish is:

- GitLab.com is fronted by Cloudflare; ordinary hosted runners are deployed in Google Cloud `us-east1`. [GitLab.com settings](https://docs.gitlab.com/user/gitlab_com/)
- Most Codeberg services run on Codeberg-owned hardware in Berlin, with some offload to other German providers. [Codeberg hosting](https://docs.codeberg.org/getting-started/faq/)
- Bitbucket Cloud data is held across two availability zones in US-East; Bitbucket is not listed among the Atlassian products that can be pinned to Singapore, Japan, or other residency regions. [Atlassian cloud architecture](https://www.atlassian.com/trust/reliability/cloud-architecture-and-operational-practices), [data residency scope](https://support.atlassian.com/security-and-access-policies/docs/understand-data-residency/)
- Azure DevOps Services offers Asia Pacific as a data location but not mainland China. It is available only in Azure's public cloud; National cloud subscriptions, including the separately operated China cloud, are unsupported for Azure DevOps billing. [Azure DevOps data locations](https://learn.microsoft.com/en-us/azure/devops/organizations/security/data-location?view=azure-devops), [billing FAQ](https://learn.microsoft.com/en-us/azure/devops/organizations/billing/billing-faq?view=azure-devops)

**Inference:** GitLab cannot win the China criterion from documentation alone, and Azure's “Asia Pacific” location cannot be assumed to be a mainland endpoint. The final choice must be based on an actual two-machine acceptance test from the maintainer's Windows workstation and MacBook, using web login, SSH/HTTPS Git, REST API, artifact transfer, and hosted-runner egress to the retained Cloudflare/Supabase services. A one-time successful page load is not enough.

## GitLab caveats that must remain visible

1. **Compute must be measured.** Free's 400 minutes may be sufficient for development checks but may be too small for the Daily/Monthly data pipeline. Buy one-time minute packs only after a secret-free representative run establishes the monthly estimate; do not jump directly to $29/month Premium merely for CI capacity.
2. **Native blocker semantics are Premium.** Free still provides labels and a child hierarchy. Preserve explicit portable `blocked_by` metadata rather than upgrading only for blocking links.
3. **GitLab export is migration assistance, not backup.** Keep regular Git mirrors/bundles and separate Issue/API exports. Do not expect variables, webhooks, artifacts, or linked-item relationships in the project archive.
4. **Mirror credentials are another secret.** A GitLab push mirror protects code against a GitLab account outage only if the destination is controlled through an independent provider/account and its credential is recoverable from the password manager.
5. **A top-level group is preferable to three personal projects.** It gives one namespace for shared CI variables, labels, visibility, and quota accounting. On Free, private top-level groups are limited to five users, which is adequate for the present personal project. Accounts created after 2026-01-27 are limited to three Free top-level groups, so use one group for this product rather than one group per repository. [Free namespace limits](https://docs.gitlab.com/user/free_user_limit/)

## Acceptance gates before selection

Run these after the independent local snapshot is verified and before live secrets or production deployment are moved:

1. Create one disposable **private** test project under the candidate namespace; do not upload a production repository or `.env` file.
2. From both the Windows workstation and MacBook, verify web login/recovery setup, SSH and HTTPS clone/push, REST API access, and a 100–500 MiB representative transfer. Record timestamps and failures.
3. Port one non-deploying Chronicle workflow to the candidate syntax and run it on the hosted Linux image. Confirm Python/Node installation, cache restore/save, artifact upload/download, log retention, UTC schedule behavior, and actual billed minutes.
4. Use dummy values to verify protected/secret-variable scoping. Do not test with Cloudflare, Supabase, Kaggle, or domain credentials.
5. Create a parent work item, child Issue/task, labels, and explicit `blocked_by` metadata. Export them, inspect the resulting archive/CSV/API JSON, and prove the portable fields survive.
6. Configure a push mirror from the disposable GitLab project to a disposable repository under a different provider/account. Push a branch and tag, then compare refs from an independent clone. Do not enable bidirectional mirroring.
7. From a hosted runner, make read-only unauthenticated requests to the public production origin and the public endpoints needed by the workflow. Later P1 design separately authorizes secret-bearing Cloudflare/Supabase tests.
8. Select GitLab if all gates pass and the measured monthly compute cost is acceptable. Select Azure DevOps only if GitLab fails a reproducible connectivity or runner requirement and accepting a private-only primary is explicit. If both fail, reopen platform research instead of defaulting to Codeberg or Bitbucket.

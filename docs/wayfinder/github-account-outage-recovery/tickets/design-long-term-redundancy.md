# Design the long-term mirror and failover topology

## Question

After development and operations are restored and GitHub has returned as the development primary, what cold-backup and failover topology protects against an entire forge account or provider becoming unavailable? Keep GitLab only while it remains a zero-cost recovery endpoint, and decide repository and Issue export direction, backup cadence and retention, secrets separation, CI reactivation readiness, periodic restore drills, account-owner risk, and the verified promotion/decommission procedures without reopening the already-decided primary roles.

## Resolution comments

### 2026-08-18 — Resolved

After GitHub has returned and the separately approved development and publication cutback has completed, use one account-wide **recovery mirror** rather than maintaining repository-specific backup workflows or a second live forge. GitHub remains the sole development, Issue, and publication primary. GitLab.com Free becomes a private, zero-cost cold recovery endpoint with one backup-only controller, one cold project per source repository, no normal product schedules, no live duplicate tracker, and no retained production deployment copies.

This decision fixes the target topology and its safety constraints; it does not authorize the cutback or create the controller. A separate Cutback & Resilience Wayfinder effort begins only if GitHub returns and owns the exact cutback plus `mirror-control` implementation handoff. If GitHub never returns, a separate permanent-primary effort must decide whether GitLab remains primary and which independent endpoint becomes its cold recovery target.

#### Account-wide topology and scope

- Create one dedicated private GitLab top-level backup group, one `mirror-control` project, one GitLab project per source GitHub repository, and no per-repository mirror scheduler. `mirror-control` is a formal fourth personal-infrastructure repository with portable repository key `mirror-control`, its own agent/tracker guidance, Issue-owned branches, tests, deployment rollback, evidence, and human merge/closure rules. Under normal operation its development and product Issues follow the GitHub primary while its GitLab copy runs the explicitly allowed backup-plane schedule. The prior personal-namespace choice remains correct for the temporary GitLab-primary recovery period; after GitHub cutback, transfer the three now-cold projects into the backup group. The accepted need for a shared service account, common policy, and automatic project discovery earns that later group migration without reopening GitHub's primary role.
- Install one read-only GitHub App on the maintainer's personal GitHub account with `All repositories`. Give it only the repository metadata, Contents, Issues, Pull requests, Releases, and other read permissions actually required by the accepted export. Use installation authentication rather than user OAuth. Each run enumerates the installation's repositories and mints a short-lived installation token; a newly owned repository is discovered without a new per-repository workflow.
- Automatically include every public, private, archived, and fork repository owned by that personal account. Organization-owned repositories require a separate installation and explicit authority. Repositories on which the maintainer is only a collaborator are not silently copied. All GitLab targets remain private regardless of the source repository's visibility.
- The Movie Cosmos acceptance guarantee covers Chronicle, the OG Worker, and Daily Stargazing. Other owned repositories use the same automatic mirror, export, and integrity checks, but Chronicle does not acquire their product, CI, deployment, or recovery-policy ownership. A repository that needs stronger provider-specific recovery semantics owns a separate decision.
- This is not a live GitHub twin. Git repositories remain immediately cloneable recovery inputs, while Issues and other forge metadata remain encrypted recovery records until a deliberate tracker promotion. GitHub Actions secrets, caches, complete run environments, forge-native identities, and provider-specific relationship behavior cannot be continuously reproduced and are not represented as synchronized truth.

#### Identity and automation boundary

- Give the backup group one GitLab service account that owns the `mirror-control` schedule and has only the group role needed to create and configure cold projects. Keep one non-expiring service-account API token, permitted by the group setting, as a deliberate no-routine-maintenance trade-off. It is scoped to the backup group, recorded in Bitwarden, installed only as a protected controller deployment copy, and has no GitHub write or production-provider authority.
- Use the service-account API token for control-plane operations such as discovering, creating, and configuring target projects. Use short-lived cross-project `CI_JOB_TOKEN` pushes for routine repository updates after each target explicitly allowlists the controller and enables job-token repository pushes. Do not create a long-lived GitLab write token per repository.
- Store the GitHub App private key and identifier in Bitwarden and install a read-only controller deployment copy. A GitHub account or provider suspension may make the App unavailable; the design promises recovery only from the last accepted off-provider recovery point, never a final post-suspension fetch.
- One genuine human maintainer remains the owner. Explicitly accept that human-availability risk rather than inventing a second identity controlled by the same person or using the restricted secondary GitHub account. GitHub and GitLab use independent sign-in, 2FA, recovery codes, and recovery email material; Bitwarden's portable export and the sealed offline record remain outside both forges.

Before the controller is admitted, a disposable secret-free trial must prove the then-current GitLab Free behavior for group service-account creation and role, the accepted token-expiration policy, API project creation/configuration, target allowlisting, and cross-project `CI_JOB_TOKEN` repository push. Any unavailable, paid-only, or materially changed capability stops admission and reopens the controller design; documentation alone is not acceptance evidence.

#### Repository and metadata flow

- Run one daily full-inventory reconciliation from GitHub to GitLab. The accepted maximum recovery-point age for intended Git refs and portable forge records is 24 hours. A run manifest records UTC start and finish, stable source and target repository IDs, source default branch, source head object IDs, exported metadata watermarks, target object IDs, file/object counts, checksums, tool versions, and final disposition.
- Synchronize only ordinary `refs/heads/*`, `refs/tags/*`, and Git LFS objects. Do not use cross-forge `git push --mirror`, and never copy GitHub pull-request refs, provider refs, remote-tracking refs, stash, reflogs, Codex refs, or unreachable objects into a forge project. The complete physical state for the three Movie Cosmos workspaces remains the restic archive's responsibility.
- Before propagating any source ref deletion or non-fast-forward rewrite, create and verify an encrypted recovery point containing the target's prior ordinary refs and metadata. After that proof succeeds, propagate the change in the same reconciliation cycle; do not add a seven-day quarantine or routine human approval. If the entire source repository disappears, the source account becomes unreadable, or inventory completeness is uncertain, retain the GitLab project unchanged and report an outage rather than interpreting absence as deletion.
- Export Issues, pull requests, ordinary comments, review comments and reviews, timeline/events, labels, milestones, releases, attachments, portable IDs, relationships, authorship text, timestamps, visibility/default-branch/protection manifests, and the raw paginated API evidence needed to reconstruct them. Keep the normalized Markdown representation from [Define the portable Issue-driven workflow](./define-portable-issue-workflow.md). Provider-native author identities, original numbers, and every relationship need not survive as native GitLab objects; the portable record must preserve the human-readable history.
- Do not continuously import those exports into GitLab Issues. GitHub remains the only writable product tracker in normal operation. Target-project Issues stay inactive; the controller may maintain one operational incident Issue in `mirror-control` because it is a backup-plane fault record, not a duplicated product Issue.
- Give `mirror-control` a separate client-side archive credential that protects only forge-derived source and metadata exports written to private R2. It must not decrypt the complete Movie Cosmos restic repository or local ignored/secret-bearing data. Mac automation copies, verifies, and retains those encrypted account exports alongside the independently restorable archive. GitLab project exports, Issue CSV, and raw provider archives remain supplemental evidence rather than the sole restore source.

#### Encrypted archives, cadence, and retention

- Keep the MacBook restic repository as the first complete recovery archive and private R2 as the second client-encrypted copy. The account-wide archive includes recoverable Git data, LFS, normalized/raw forge metadata, attachments, settings manifests, and receipts for every owned repository. The Movie Cosmos archive additionally retains the three complete worktrees and physical Git stores, ignored operational data, Daily's external gitdir, local-only refs, reflogs, stash, Codex refs, and unreachable objects already defined by [Define the complete recovery snapshot and its proof](./define-complete-recovery-snapshot.md).
- Retain 14 accepted daily recovery points and 12 accepted monthly recovery points. Retain the original `github-account-outage-pre-migration` snapshot indefinitely. Run `forget` or `prune` only after both archive locations pass their current integrity and restore checks and the retained-point manifest proves that policy will still be met.
- Refine the pre-migration snapshot's interactive-only password rule for long-term automation by adding a separate, revocable restic automation key. Keep that automation key as a scoped deployment copy in macOS Keychain and retrieve it through restic's password-command mechanism; keep the primary recovery key in Bitwarden and the sealed offline record. The automation key has full archive read capability, so loss of trust in the Mac account or Keychain triggers immediate revocation and replacement.
- Perform a silent automated integrity check every week and an automated complete non-production restore every month, alternating the MacBook and R2 sources so both copies are exercised. Run an extra complete restore after a material change to the topology, archive format, encryption/key procedure, or restore tooling.
- Restore into a restricted encrypted scratch location, compare the complete file/type/link/hash manifest, run `git fsck --full --strict` against all physical Movie Cosmos stores, fresh-clone and compare every cold repository's intended refs and LFS inventory, render the portable Issue tracker, and run the dormant non-production CI fixtures with dummy values. Do not mutate production, install production deployment copies, import a live tracker, or manufacture a publication solely for a drill. Remove only the verified scratch restore after the receipt is durable.
- Successful backup and drill runs write receipts without notifying the maintainer. Retry transient failure automatically. When the newest accepted point would exceed 24 hours, a restore/check fails, the source inventory becomes incomplete, or a free-tier limit threatens writes, create or update one incident Issue in the GitLab `mirror-control` project and notify the human owner through the watched project/account email. While GitHub is primary, a separate lightweight GitHub-side watchdog reads only the newest accepted private-R2 receipt age and GitLab/controller health; it opens or updates a GitHub incident and uses GitHub account email when GitLab cannot report for itself. During a GitHub outage the GitLab controller remains the reporting side. Simultaneous loss of both reporting planes is an explicit residual risk covered only by the last accepted Mac/R2 recovery point. Close an incident automatically only after a new accepted run proves recovery.

#### Cold CI and secrets posture

- Disable CI/CD on every mirror target while it is cold. Keep only the reviewed provider-neutral scripts, disabled adapters, configuration manifests, and non-production fixtures required to prove reactivation readiness. The active GitLab `mirror-control` schedule and the GitHub-side receipt watchdog are reciprocal backup-plane exceptions to the prohibition on duplicate product schedules; neither is a development, product-test, deployment, Site, Data, Monthly, or Recovery schedule.
- After the initial GitLab-to-GitHub cutback and after every future failback, delete or revoke all GitLab production deployment copies. Bitwarden remains the secrets authority. A failover reissues and installs fresh least-privilege copies only after a human Go and the relevant P1 inventory and authorization gates.
- Never put the Bitwarden session, offline restic recovery key, complete-archive automation key, Cloudflare/Supabase/Kaggle credentials, or any production token in `mirror-control`. Backup-plane credentials and production deployment copies have separate issuers, scopes, consumers, evidence, and revocation paths.
- CI readiness proves only that the disabled adapters still validate and the shared entry points pass non-production fixtures. It does not pre-authorize production, turn on Monthly, or convert Production Recovery into hosted execution. Monthly remains suspended during every GitLab-primary interval, and Recovery remains the local audited planner plus repository-owned commands already decided by [Design the P2 Monthly and Production Recovery path](./design-p2-recovery-path.md).

#### Verified promotion and failback

On a declared GitHub account or provider outage, stop reconciliation before accepting writes on GitLab and choose the newest accepted recovery point. Automation prepares the evidence, but promotion is never automatic:

1. verify the recovery point is no older than 24 hours or explicitly record the known gap;
2. fresh-clone each affected project, compare intended heads/tags and LFS, run `git fsck`, verify private visibility/default branch/protection settings, render the normalized Issue export, and verify portable IDs and relationships;
3. promote the normalized export to the sole writable local Markdown tracker first, record the failover time and source point, then import and verify it before promoting GitLab as the one active remote tracker;
4. obtain one human Go, enable only the minimal non-deploying CI, and make each repository pass its existing development-resume gate; and
5. transfer publication authority separately through the P1 drain, inventory, credential, manual-run, smoke, and receipt gates. Monthly remains suspended and local Recovery retains its takeover checks.

When GitHub returns, do not resume mirroring over divergent GitLab-primary state. Freeze writes, capture GitHub's returned refs and Issue metadata into isolated recovery inputs, capture GitLab/local state, and reconcile with human approval. Push only explicit accepted heads/tags/LFS to GitHub; import portable Issue history with recorded identity/number degradation; prove GitHub's protected branches, one active tracker, and non-deploying delivery cycle; then perform the separately approved publication cutback. Only after GitHub is again authoritative may the controller reseed GitLab, remove every GitLab production deployment copy, and return the group to cold status.

#### Free-tier gates and decommission

- Optimize the daily controller for changed repositories and monitor GitLab namespace compute and per-project repository/LFS storage. Prefer the GitLab hosted schedule while it remains inside the free allowance. If shared-runner capacity cannot meet the 24-hour objective without payment, move the same controller to automated Mac `launchd`; do not buy minutes or introduce a self-hosted runner merely to preserve the mirror. If neither execution path meets the objective, the cold endpoint has failed admission and the host choice must be reopened.
- Do not purchase storage automatically. When one repository approaches GitLab Free's per-project repository/LFS limit, retain its accepted Mac/R2 archives, stop before the target becomes read-only, and open a new endpoint-selection Wayfinder effort for that repository only. Other compliant cold projects remain in service.
- Decommission the whole GitLab backup group only when GitLab ceases to provide the required path at zero cost, the controller cannot meet the accepted objective, or repeated verified failures make it a material maintenance burden. Replacement or decommission execution requires a new host-selection Wayfinder effort; Azure DevOps is not silently promoted by this ticket.
- Before any project or group deletion, stop new source changes or take a final consistent inventory, complete the final explicit-ref/LFS sync and normalized metadata export, verify both encrypted archives, fresh-clone and run `git fsck`, render the Issue records, record the final receipt and provider aliases, revoke the GitHub App/controller/R2 deployment copies, and obtain human deletion approval. Never auto-delete a cold project because its source disappeared or its provider announced a pricing change.

Implementation is planning handoff, not part of this map. The follow-on Cutback & Resilience effort owns a Chronicle integration Issue, repository-owned cutback Issues for every repository it actually changes, and the `mirror-control` implementation Issue; it decides their exact dependencies only after returned GitHub state is captured. Chronicle owns the Movie Cosmos policy, integration gates, and evidence, while the controller belongs to `mirror-control` and any other repository-local adapter change remains Issue-owned in that repository. The human risk declaration for the Chronicle integration/cutback delivery uses R3 with canonical surfaces `publication`, `planet_export`, `og_worker`, and `daily`; private source and forge metadata, Git/LFS recovery history, encrypted archives, backup identities/credentials, and failover control belong in declaration notes and the `mirror-control` repository's own accepted risk vocabulary. A mirror or drill never grants production authority.

Primary capability constraints used by this decision are documented by GitHub's [GitHub App installation](https://docs.github.com/en/apps/using-github-apps/installing-your-own-github-app), [installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app), and [repository backup](https://docs.github.com/en/repositories/archiving-a-github-repository/backing-up-a-repository) guidance; GitLab's [repository mirroring](https://docs.gitlab.com/user/project/repository/mirror/), [service accounts](https://docs.gitlab.com/user/profile/service_accounts/), [service-account token expiration](https://docs.gitlab.com/user/profile/personal_access_tokens/#create-a-service-account-personal-access-token-with-no-expiry-date), [CI job-token push](https://docs.gitlab.com/ci/jobs/ci_job_token/), [project export omissions](https://docs.gitlab.com/user/project/settings/import_export/), and [storage limits](https://docs.gitlab.com/user/storage_usage_quotas/); and restic's [multiple-key and automated password support](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html) and [macOS Keychain example](https://restic.readthedocs.io/en/latest/faq.html#how-can-i-specify-encryption-passwords-automatically).
